## Inventory Item create: study and decisions open

[Inventory route](../backend/app/api/routes/inventory.py) requires `storage.items` or wildcard and calls [stock service](../backend/app/models/inventory/stock_service.py) with [ItemIn](../backend/app/libs/dto/inventory/item_input.py). Service additionally enforces category access, checks exact raw SKU, normalizes payload and checks active-name groups before direct Item add/flush, audit, commit and refresh. Its `_item_payload` is shared with update. The normal [Master Data producer](../frontend/src/app/%28app%29/inventory/master-data/page.tsx) trims/generates values and filters composition differently from the API; neither producer exhausts external clients.

A focused typed normalized insert command and schema-owned supplied-session add/flush is a possible seam, not an approved implementation. Category and unit remain strings pending actual stored values, producers, consumers and owner vocabulary decisions; do not infer exhaustive enums from UI choices. Preserve raw SKU behavior, decimal rounding, active/inactive name checks, image URL validation and composition shape/threshold. Image upload and seed are separate writers. Existing [numeric bounds tests](../backend/app/tests/test_inventory_item_numeric_bounds.py) do not prove complete create parity.

Before implementation resolve command shape/home and serialize ownership of shared normalization with update. Verification should compare old/new accepted and refused inputs, role and validation precedence, output and persisted values, audit and rollback/retry, duplicate and concurrent behavior on an isolated PostgreSQL target, and update-path parity. Actual UI creation/readback and adjacent receiving or purchasing selection should avoid creating stock; report image and role coverage accurately. Human business acceptance and production deployment remain separate.
