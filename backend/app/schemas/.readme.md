# Schemas: validated API contracts (DTOs)

Reuse the existing Pydantic schemas. In this project they are DTOs; the database
schema models are SQLAlchemy models in models/. These files do not perform CRUD.

- Create: required creation inputs and intentional defaults. Server-controlled
  identity, audit and derived totals come from trusted code, not client authority.
- Update: only fields the operation allows to change. For partial updates use
  model_dump(exclude_unset=True); omitted is different from explicitly null.
  Define which fields may be cleared. Never reuse creation defaults as patch values.
- Read/Out: explicit public response shape; omit passwords, secrets and internal
  fields. Add a query/filter schema only when the input contract needs it.
- Ordinary and privileged updates may need separate contracts/permissions. Schema
  membership is not authorization; the service still checks the actor and object.
- Reuse domain enums with unchanged string values. New validation, extra-field
  rejection, renamed values, null rules or response fields can break callers:
  identify and review those behavior changes separately from a code move.

Existing names such as UserIn/UserUpdate/UserOut already cover these roles. Avoid
mass renaming for aesthetics. No parallel dto/ or libs/dto/ directory. Default
factories in Pydantic, Python ORM defaults and server defaults have different
execution points; preserve existing behavior deliberately.

Ismail coordinates conventions; feature owners migrate their callers and tests.
