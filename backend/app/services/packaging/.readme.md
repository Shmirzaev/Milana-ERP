# Packaging services: package lifecycle operations

This folder documents the proposed packaging service organization. Existing
service files, router code, and database behavior have not been moved or changed.

## Purpose

Give package-related operations a clear owner and supported entry points, using
the mentor's feature-service discipline. Group operations here when their
refactor is approved, while keeping genuinely separate responsibilities clear.

## What belongs here

- Package creation and correction rules, including selected-batch quantities and
  partial packages.
- Shared package identity and label eligibility rules used by multiple callers.
- Print-run and return operations belonging to the package lifecycle.

Warehouse receipt, stock, and shipment operations retain their own ownership.
Document their handoff with Packaging and use their supported operations when a
workflow spans features.

## First known dependency to remove

`app/services/package_workflows.py` currently imports the private
`_package_lookup_candidates` helper from `app/api/routes/packages.py`. The shared
rule belongs below the HTTP layer. Review existing `package_identity.py` and
`legacy_package_identity.py` before choosing its final home so we consolidate the
rule instead of adding another competing parser.

## Rules

- Routers handle HTTP input/context and responses; services own package rules.
- Services must not import routers or call their private helpers.
- Preserve canonical codes, legacy aliases, ambiguous-code rejection, outdated
  label rejection, authorization, and audit history.
- Related writes succeed or fail together under one transaction owner.
- Receiving or returning a package must preserve stock and reservation evidence.
  Do not remove guards to make a blocked action succeed.
- Reuse existing `app/schemas/` contracts and introduce stable vocabulary through
  `app/enums/` only when converting its callers.
- Test the affected Packaging-to-Warehouse-to-Shipment handoff.
