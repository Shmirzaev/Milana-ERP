# Services: business operations

Services own business rules, object/factory authorization and coordinated ORM CRUD.
Routers, jobs and approved other features call named operations through their agreed
interface. Use existing feature services before adding a new one.

- Humans agree service responsibilities and public operations. Split by business
  ownership and transaction needs, not number of endpoints, tables or lines.
- Accept SQLAlchemy Session and actor/context explicitly. Models describe storage;
  Pydantic DTOs describe input/output. No mandatory repository or interface layer.
- One outer operation owns commit/rollback. Helpers can flush when appropriate but
  cannot independently commit the caller's work. Preserve existing lock order,
  autobegin behavior, idempotency, audit and notification/queue timing.
- Reuse the permission evaluator. An enum or hidden frontend button is not RBAC.
- No service-to-router imports, endpoint calls or private cross-feature helpers.
  For new operations, keep FastAPI Request/Depends/response objects at the HTTP edge;
  record any legacy exception instead of hiding a behavior change in extraction.
- Test contracts, changed database state, refusal paths and the department handoff.
  Use isolated PostgreSQL for locks/constraints rather than assuming SQLite parity.

Temporary legacy/new implementations are allowed only for the approved switch
process, with one selected write path, parity checks and a cleanup owner. Do not
create a general-purpose flag framework. Keep fixes synchronized until retirement.

production.py already exists: do not shadow it by adding production/__init__.py
without a coordinated conversion. See the [team plan](../../../docs/REFACTOR_PLAN.md).
