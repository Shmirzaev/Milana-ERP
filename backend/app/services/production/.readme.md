# Production services: owned business operations

This is a documentation-only folder for the proposed production refactor.
Existing Python files and imports remain in place.

## Purpose

Keep related production rules behind named operations that routes and other
approved callers can reuse. The mentor's resolver-to-service separation becomes
FastAPI router-to-service separation here.

The proposed first operation is `record_sewing_output`. Ordinary Sewing and band
Sewing should eventually call that operation instead of one HTTP handler calling
another. A future `sewing.py` would own Sewing operations; a future `cutting.py`
would own Cutting operations when that separate refactor is approved.

## What belongs here

- Production quantity checks and workflow transitions.
- Database-dependent prerequisites and object-level access checks.
- Coordinated writes, audit records, retry behavior, and transaction ownership
  for a complete production operation.
- Shared production rules with an explicit owner and documented callers.

## Rules

- Accept the database session and authenticated context explicitly.
- Reuse existing authorization evaluators. A refactor must preserve their
  behavior; an intentional permission correction is a separate reviewed change.
- Services must not import routers, call HTTP handlers, or use private helpers
  from another feature. Use that feature's supported operation.
- Keep related writes atomic. The outer operation owns commit/rollback; internal
  helpers participate without committing the caller's work.
- Preserve lock ordering, idempotency, audit behavior, and existing API contracts.
- Preserve the recent receipt/input reconciliation: 600 received pieces must
  allow recording 495 followed by 105 without counting the receipt twice. Keep
  separate Nastils independent and unfinished work reachable.
- Verify both Sewing callers, corrections, and the affected department handoff.

## Existing filename requires a coordinated migration

`app/services/production.py` already exists. This directory deliberately contains
only this guide and has no `__init__.py` or implementation files. The existing
`app.services.production` import continues to resolve to that file.

Do not add a package initializer alongside the old file: it can shadow the old
module. When implementation is approved, inspect every caller and convert the
file to a package in one reviewed change, preserving or explicitly updating its
supported imports. A short-lived legacy/new operation pair is allowed only for the approved switch
process in the team plan, with one write path, parity checks and a cleanup owner.
Do not retain competing implementations after acceptance.
